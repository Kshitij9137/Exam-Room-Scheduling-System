# **Final Merged Development Plan: Exam & Room Scheduling System**



Recommended final blueprint

7 development phases



**Technology stack:** Python · Django · Django Templates · Bootstrap 5 · JavaScript · SQLite

**Project objective:** Build a complete, reproducible and explainable university examination scheduling system that automatically assigns examinations to suitable time slots, rooms and invigilators while respecting student enrollment, room capacity, equipment, availability and student accommodations.

This plan uses **Plan 2 as the main development roadmap**, incorporating Plan 1's three-tier architecture and dashboard, and Plan 3's traceability, decision explanations and constraint scorecard.

The seven phases are arranged in implementation order, starting with database design and ending with testing, reproducibility and final demonstration.

# **1. System Architecture — Three-Tier Architecture**

The application must follow a clear separation between presentation, business logic and data storage.

**TIER 1 — PRESENTATION**

Frontend

**Django Templates + Bootstrap 5 + JavaScript**

- Executive dashboard
- Examination timetable
- Exam details and allocation explanations
- Student lookup
- Exceptions and validation reports
- Conflict graph visualization
- Role-based interface

HTTP requests and responses

**TIER 2 — APPLICATION**

Backend

**Django Views + Forms + Python Services**

- Synthetic data generator
- Conflict graph engine
- Scheduling algorithm
- Room allocation engine
- Invigilator allocation engine
- Accommodation processor
- Independent validation engine
- Anomaly detection and evaluation
- Audit and reporting services

Django ORM and transactions

**TIER 3 — DATA**

Database

**SQLite + Django ORM**

- 11 required domain entities
- Supporting relational entities
- Scheduling runs and assignments
- Event and audit history
- Validation reports
- CSV/JSON exports
- Separate ground-truth evaluation artifacts

### **Architectural principles**

1. Django Templates must only handle presentation.
2. Django Views must handle HTTP requests and responses, not scheduling algorithms.
3. Business rules must reside in reusable Python service modules.
4. Management commands and frontend actions must call the same service functions.
5. Every scheduling execution must be independently identifiable.
6. Historical assignments and events must never be silently overwritten.
7. The scheduler must not access the ground-truth labels.
8. All important decisions and exceptions must be explainable.

You do not need Django REST Framework, React, Celery or PostgreSQL for this implementation. A single Django application can implement all three logical tiers.

### **Subphase 1.2 — Define business rules**

Write every rule in a separate document before coding.

**Hard constraints — must never be violated:**

| Rule | Description                                                |
| ---- | ---------------------------------------------------------- |
| H1   | A student cannot have two overlapping examinations         |
| H2   | Allocated students cannot exceed room capacity             |
| H3   | Required room equipment must be available                  |
| H4   | Rooms must be available throughout the examination         |
| H5   | Invigilators must be available and cannot be double-booked |
| H6   | Student accommodations must be respected                   |
| H7   | A room cannot host overlapping examinations                |

**Soft constraints — improve scheduling quality:**

- Avoid back-to-back examinations for students.
- Distribute examinations across available days.
- Minimize unnecessary room-capacity wastage.
- Balance invigilator workloads.
- Avoid excessively long examination days.

Soft constraints may influence the quality of the schedule but must never override hard constraints.

Document assumptions such as examination periods, slot lengths, transition buffers, invigilator staffing ratios and accommodation policies. These are configurable university policies, not fixed values supplied by the problem statement.

For `Availability`, use two nullable foreign keys (`room_id` and `invigilator_id`) with a database constraint requiring exactly one to be populated. This keeps actual foreign-key integrity without a generic `target_id`.

Add the following supporting entities:

| Supporting entity     | Purpose                                           |
| --------------------- | ------------------------------------------------- |
| RoomClosure           | Track temporary room closures                     |
| TimeSlot              | Define valid examination slots                    |
| SchedulerRun          | Record every scheduling execution                 |
| ScheduleEvent         | Maintain append-only decision and change history  |
| InvigilatorAssignment | Connect multiple invigilators to room assignments |
| StudentRoomAllocation | Track the exact room allocated to each student    |
| UnassignedExam        | Store unscheduled exam details and reason codes   |
| ValidationRun         | Store independent validation executions           |
| DetectedViolation     | Store the actual violations detected              |

**Important relationship decisions:**

- Student and Course have an N:M relationship through Enrollment.
- Exam and Room can have an N:M relationship through ScheduleAssignment.
- One exam may require multiple rooms.
- One room allocation may have multiple invigilators.
- Every allocated student must be linked to an actual room allocation.
- Each scheduling run must preserve its own assignment records.

For multiple-room support, create one `ScheduleAssignment` record per exam-room allocation. All room allocations for the same exam within a run must be consistent with its planned start time. A separate `UnassignedExam` record should be created when a complete feasible allocation cannot be made.

## **Phase 4 — Core Scheduling Engine and Conflict Resolution**

Most important technical phase

**Goal:** Build the actual scheduling engine that allocates exams while respecting all hard constraints.

Keep scheduling algorithms in plain Python services. This makes them independently testable and reusable from both Django views and management commands.

### **Subphase 4.1 — Build the conflict graph**

Represent examinations as graph vertices.

Two examinations are connected when at least one student is enrolled in both.

Example:

```
       EXAM-001
       /     \
  EXAM-002  EXAM-003
       \     /
       EXAM-004
```

The edge weight should represent the number of shared students.

Create:

```
apps/scheduling/services/conflict_graph.py
```

The graph should be generated using active enrollments only.

### **Subphase 4.2 — Implement exam ordering using DSatur**

Use the DSatur graph-coloring heuristic.

The algorithm prioritizes examinations by:

1. Highest saturation degree.
2. Highest conflict degree.
3. Largest student enrollment.
4. Most restrictive room and equipment requirements.

Each color represents an examination time group.

Exams connected by an edge must receive different, non-overlapping time groups.

Implement this in plain Python first. NetworkX is optional, not mandatory.

### **Subphase 4.3 — Implement candidate time-slot selection**

Create:

```
apps/scheduling/services/slot_allocator.py
```

For every exam:

- Identify eligible dates and candidate slots.
- Check student conflicts.
- Confirm the slot can accommodate examination duration.
- Include required accommodation time.
- Respect operating hours and time buffers.
- Try another candidate if the current one is infeasible.

Use actual time intervals, not just slot labels, for final conflict validation.

### **Subphase 4.4 — Implement room allocation**

Create:

```
apps/scheduling/services/room_allocator.py
```

Check:

- Room is active.
- Capacity is sufficient.
- Required equipment is available.
- Accessibility requirements are satisfied.
- Room availability covers the entire allocation.
- No closure overlaps the allocation.
- Room is not already occupied by another exam.

Use best-fit allocation: choose the smallest suitable room or combination of rooms that can accommodate the students.

Support multiple rooms for a single examination.

Use `StudentRoomAllocation` to identify exactly which students are assigned to each room.

### **Subphase 4.5 — Implement accommodation handling**

Create:

```
apps/scheduling/services/accommodation.py
```

Example:

| Examination | Accommodation | Required duration |
| ----------- | ------------- | ----------------- |
| 120 minutes | None          | 120 minutes       |
| 120 minutes | 25% extra     | 150 minutes       |
| 120 minutes | 50% extra     | 180 minutes       |
| 120 minutes | 100% extra    | 240 minutes       |

Calculate:

\\[ D\_{\text{required}} = D\_{\text{base}} \times \left(1+\frac{\text{extra time percentage}}{100}\right) \\]

Requirements:

- Apply only effective accommodations.
- Allocate separate rooms when required.
- Ensure accessible-room requirements are satisfied.
- Reserve rooms and invigilators for their required durations.
- Do not cut off extended-time students when the base exam ends.

For multiple student groups in different rooms, each room's allocation should have an end time sufficient for the students assigned to it.

A conservative first implementation can reserve the full maximum required duration for all students sharing a room.

### **Subphase 4.6 — Implement invigilator allocation**

Create:

```
apps/scheduling/services/invigilator_allocator.py
```

Rules:

- Invigilator must be available.
- Invigilator cannot be double-booked.
- Assigned duration must fit availability.
- Daily working-hour limits must be respected.
- Consecutive-hour limits must be respected.
- Every room must have the required staffing level.

Use a documented, configurable staffing policy, such as a minimum of one invigilator per room and one additional invigilator for every 50 students.

### **Subphase 4.7 — Add traceable decision-making**

Create:

```
apps/scheduling/services/explanations.py
```

Every scheduling decision should record:

- Exam selected.
- Candidate times considered.
- Rooms considered.
- Reasons for room rejection.
- Invigilators considered.
- Selected resources.
- Final outcome.
- Algorithm version.
- Relevant constraint evidence.

For example:

```
EXAM-2026-000042

STATUS: UNASSIGNED

PRIMARY REASON:
NO_ROOM_CAPACITY

Largest eligible room:

```

### **Subphase 4.8 — Preserve scheduling history**

Create a `SchedulerRun` for every execution.

For example:

```
RUN-000001
    EXAM-001 -> ROOM-001 -> 09:00

RUN-000002
    EXAM-001 -> ROOM-003 -> 09:00
```

Use `ScheduleEvent` to record assignment creation, rescheduling, cancellation and unassignment.

Use `transaction.atomic()` so a partially allocated examination cannot leave inconsistent room or invigilator records behind.

## **Phase 5 — Independent Validation, Edge Cases and Evaluation Metrics**

Mandatory evaluation phase

**Goal:** Prove that the generated schedule is correct and that the system can independently detect deliberate violations.

This phase must be independent of the scheduling algorithm.

### **Subphase 5.1 — Build the independent schedule validator**

Create:

```
apps/validation/services/schedule_validator.py
```

The validator must examine the persisted database records.

It should independently check:

- Student overlapping examinations.
- Room capacity violations.
- Missing equipment.
- Invigilator overlapping assignments.
- Accommodation violations.
- Room closures and availability.
- Invalid examination durations.
- Student-room allocation reconciliation.

Do not simply call the scheduler's in-memory feasibility methods again. Use separate checks over persisted data so both systems cannot silently share the same implementation defect.

Persist the results through `ValidationRun` and `DetectedViolation`.

### **Subphase 5.2 — Generate the five mandatory anomaly scenarios**

Maintain two distinct datasets or test scenarios.

**Scenario A — Valid baseline**

Expected result: zero hard violations

Generate valid data → Run scheduler → Run independent validator.

**Scenario B — Deliberate anomalies**

Expected result: five anomaly types detected

Create deliberately invalid assignments → Run detector → Compare results with ground truth.

The five required cases:

| Scenario                       | Deliberate violation                                                            | Expected detection           |
| ------------------------------ | ------------------------------------------------------------------------------- | ---------------------------- |
| Student overlapping exams      | Same student assigned to two overlapping exams                                  | `STUDENT_DOUBLE_BOOKING`     |
| Room capacity exceeded         | 120 students assigned to a 50-seat room                                         | `ROOM_CAPACITY_EXCEEDED`     |
| Invigilator double-booked      | Same invigilator assigned to two overlapping exams                              | `INVIGILATOR_DOUBLE_BOOKED`  |
| Accommodation ignored          | Extended-time student receives insufficient examination time or unsuitable room | `ACCOMMODATION_VIOLATION`    |
| Exam outside room availability | Exam assigned during room closure                                               | `ROOM_UNAVAILABLE_VIOLATION` |

Each test fixture must contain a real database condition that violates the rule.

```
EDGE-001,STUDENT_OVERLAP,STU-000123,STUDENT_DOUBLE_BOOKING
EDGE-002,CAPACITY_EXCEEDED,ROOM-000012,ROOM_CAPACITY_EXCEEDED

```

The ground-truth file must not be part of the detector's input.

It is only used by the evaluation service after detection has completed.

### **Subphase 5.4 — Implement anomaly detection and evaluation**

Create:

```
apps/validation/services/
    anomaly_detector.py
    evaluator.py
```

Implement:

- Detection of actual database violations.
- Comparison of detected cases with expected labels.
- True positive calculation.
- False positive calculation.
- False negative calculation.
- Precision, recall and F1-score.

\\[ Precision=\frac{TP}{TP+FP} \\]

\\[ Recall=\frac{TP}{TP+FN} \\]

\\[ F1=2\times\frac{Precision\times Recall}{Precision+Recall} \\]

Calculate these metrics from actual results. Never hardcode a 100% score.

### **Subphase 5.5 — Add constraint scorecard**

Show each rule and its validation status.

| Constraint               | Checks performed | Failures      | Status    |
| ------------------------ | ---------------- | ------------- | --------- |
| Student conflicts        | Actual result    | Actual result | Pass/Fail |
| Room capacity            | Actual result    | Actual result | Pass/Fail |
| Equipment                | Actual result    | Actual result | Pass/Fail |
| Invigilator availability | Actual result    | Actual result | Pass/Fail |
| Accommodation            | Actual result    | Actual result | Pass/Fail |
| Room availability        | Actual result    | Actual result | Pass/Fail |

The scorecard must reflect the selected validation run.

### **Subphase 5.6 — Calculate business metrics**

Include:

| Metric                       | Description                                                            |
| ---------------------------- | ---------------------------------------------------------------------- |
| Scheduling coverage          | Percentage of exams completely scheduled                               |
| Hard constraint violations   | Total violations in the normal baseline                                |
| Student allocation rate      | Percentage of eligible student-exam enrollments successfully allocated |
| Room seat utilization        | Allocated student seats / capacity of rooms used                       |
| Room time utilization        | Booked room-minutes / available room-minutes                           |
| Invigilator utilization      | Assigned invigilator-hours / available hours                           |
| Exception documentation rate | Unassigned exams with documented reasons                               |
| Detection precision          | Correct reported violations / all reported violations                  |
| Detection recall             | Detected actual violations / all actual violations                     |
| Detection F1                 | Combined precision and recall                                          |
| Scheduler execution time     | Actual time taken by the scheduling run                                |

Also enforce these reconciliation checks:

```
Total exams
    =
Completely scheduled exams
    +
Unassigned exams
```

For every completely scheduled exam:

```
Active enrolled students
    =
Allocated students
```

Any mismatch should produce an explicit validation error.

# **4. Final Management Command Workflow**

Your project should support a straightforward execution flow.

```
# 1. Create the database
python manage.py migrate

# 2. Generate synthetic records
python manage.py generate_data --seed 20261022 --scale full

# 3. Validate source data
python manage.py validate_data

# 4. Run examination scheduling
python manage.py run_scheduler

# 5. Independently validate the schedule
python manage.py validate_schedule

# 6. Create deliberate anomaly test fixtures
python manage.py inject_anomalies

# 7. Detect violations
python manage.py detect_violations

# 8. Evaluate anomaly detection
python manage.py evaluate_anomalies

# 9. Export data and reports
python manage.py export_data

# 10. Verify reproducibility
python manage.py verify_reproducibility --seed 20261022

# 11. Run all automated tests
python manage.py test
```

The anomaly commands should operate on an isolated test scenario or dedicated fixture run. They must not contaminate the clean baseline used to demonstrate zero violations.
